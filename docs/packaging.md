# Packaging and releases

Este documento explica opciones para distribuir o probar TaskManager de forma más rápida.

---

## ¿Tiene sentido subir un paquete instalable?

Para este tipo de práctica, normalmente **no hace falta crear un instalador**.

El proyecto está formado por:

- Backend ASP.NET Core.
- Frontend React.
- Base de datos SQL Server.

No es una aplicación de escritorio tradicional, por lo que un instalador `.exe` no suele ser necesario.

Lo más recomendable es:

1. Subir el código completo a GitHub.
2. Crear tags de versión.
3. Crear una release en GitHub.
4. Incluir instrucciones claras de instalación en el README y en `docs/`.

---

## Opción recomendada para la práctica

Usar GitHub Releases con código fuente.

Ejemplo:

```text
Release: v0.2.0-frontend
Descripción: Full backend and frontend implementation completed.
Assets: Source code generated by GitHub.
```

GitHub genera automáticamente:

```text
Source code (zip)
Source code (tar.gz)
```

Esto suele ser suficiente para que cualquiera descargue el proyecto y lo ejecute siguiendo la documentación.

---

## Build del frontend

Se puede generar una versión estática del frontend:

```bash
cd TaskManager.Client
npm run build
```

Esto genera:

```text
TaskManager.Client/dist/
```

Esa carpeta contiene archivos estáticos de producción.

No suele subirse al repositorio, porque se puede regenerar con `npm run build`.

---

## Publicar backend en carpeta

Se puede publicar el backend en una carpeta:

```bash
cd TaskManager.Api
dotnet publish -c Release -o publish
```

Esto genera:

```text
TaskManager.Api/publish/
```

Esa carpeta contiene una versión publicada del backend.

Tampoco suele subirse al repositorio, porque se puede regenerar.

---

## Paquete ZIP manual

Si se quiere entregar un paquete rápido, se podría crear un ZIP con:

```text
TaskManager.Api/publish/
TaskManager.Client/dist/
README.md
docs/
```

Pero habría que tener en cuenta:

- El usuario seguirá necesitando SQL Server.
- El usuario seguirá necesitando configurar `appsettings.json`.
- El usuario seguirá necesitando aplicar o tener base de datos.
- El frontend estático necesita apuntar al backend correcto.

Por eso, para una práctica, puede añadir complejidad innecesaria.

---

## Recomendación final

Para este proyecto, lo mejor es:

- No subir `dist/`.
- No subir `publish/`.
- No crear instalador.
- Sí crear tags.
- Sí crear una GitHub Release.
- Sí dejar documentación clara.

---

## Archivos que no deberían subirse

Comprobar `.gitignore` para evitar:

```text
bin/
obj/
.vs/
TaskManager.Api/Logs/
TaskManager.Client/node_modules/
TaskManager.Client/dist/
TaskManager.Api/publish/
```

## Comandos útiles

Crear build de frontend:

```bash
cd TaskManager.Client
npm run build
```

Publicar backend:

```bash
cd TaskManager.Api
dotnet publish -c Release -o publish
```

Crear tag:

```bash
git tag -a v0.2.0-frontend -m "Frontend implementation completed"
git push origin v0.2.0-frontend
```
